# To3mato 서버 연동 및 커뮤니티 기능 설계 논의

작성일: 2026-10-20
상태: 2026-10-20 결정 완료. 순서 1(동기화 우선)과 Supabase로 진행한다. 플랫폼은 같은 날 Cloudflare Workers에서 Supabase로 바꿨다. 0·1단계 상세 설계는 `docs/sync-design.md`에 있다.

## 목표

서버를 붙이는 이유는 세 가지로 나뉜다. 서로 독립이며 한 번에 전부 할 필요가 없다.

| 역할        | 사용자에게 주는 것                                                 | 필요한 것                        |
| ----------- | ------------------------------------------------------------------ | -------------------------------- |
| 백업·동기화 | 기기를 바꾸거나 두 대를 써도 할 일과 기록이 같다. 데이터 유실 방지 | 계정, 변경 로그, 충돌 처리       |
| 커뮤니티    | 다른 사람과 포모도로 기록을 공유한다. 함께 집중한다                | 계정, 공유 데이터 모델, 그룹     |
| 계정        | 위 둘의 전제. 그 자체로는 기능이 아니다                            | 로그인, 세션, 탈퇴와 데이터 삭제 |

범위 밖: 서버 측 AI, 결제, 공개 피드. 이 문서는 macOS 데스크톱 앱을 기준으로 한다. 브라우저 미리보기는 서버 기능을 지원하지 않는 쪽으로 제안한다.

## 현재 상태

| 항목        | 현재                                                                                            |
| ----------- | ----------------------------------------------------------------------------------------------- |
| 데이터      | `userData/to3mato.sqlite3`. `projects`·`tasks`·`focus_records`·`settings`·`timer` 5개 테이블    |
| 상태 처리   | 렌더러가 `Command`를 보내고 메인이 `applyCommand`로 새 상태를 만든 뒤 전체 상태를 돌려준다      |
| 저장 방식   | `storage.mjs`가 이전 상태와 다음 상태를 행 단위로 비교해 바뀐 행만 쓴다                         |
| 기록 ID     | `focus_records.id`는 배열 인덱스(`index + 1`)로 저장할 때마다 다시 계산한다. 안정적인 ID가 없다 |
| 영상        | 3초 클립과 주간 영상 편지는 렌더러 IndexedDB. SQLite와 JSON 백업에 포함되지 않는다              |
| 네트워크    | 메인 프로세스의 업데이트 피드 조회뿐. 렌더러 CSP는 `connect-src 'self'`                         |
| 보안 구조   | 렌더러 sandbox + contextIsolation. IPC는 `trusted(event)` 검사                                  |
| 인프라      | Cloudflare Pages(사이트), R2(다운로드), wrangler 로그인. `doyeong.dev` 하위 도메인 사용 중      |
| 계정        | 없음. 앱은 네트워크 없이 전부 동작한다                                                          |
| 도메인 로직 | `src/lib/domain.mjs`는 Node·브라우저 의존성이 없는 순수 ESM. 서버에서도 그대로 실행할 수 있다   |

## 설계 원칙

1. 로컬 우선. 계정이 없어도 지금처럼 전부 동작한다. 서버는 선택 기능이다.
2. 오프라인에서 쓴 변경은 로컬에 쌓였다가 연결되면 올라간다. 네트워크 오류로 작업이 막히지 않는다.
3. 할 일 제목과 프로젝트 이름은 동기화에만 쓰고 커뮤니티에는 내보내지 않는다. 공유 단위는 포모도로 수와 집중 시간이다.
4. 공유는 전부 명시적이다. 그룹 참여와 클립 공유는 사용자가 항목마다 직접 선택한다.
5. 네트워크 호출과 토큰 보관은 메인 프로세스가 한다. 렌더러 CSP와 IPC 검사는 지금 구조를 유지한다.
6. 커뮤니티 데이터와 동기화 데이터를 분리한다. 동기화를 켜지 않아도 커뮤니티를 쓸 수 있고 그 반대도 된다.
7. 탈퇴하면 서버의 모든 데이터를 지운다. 로컬 데이터는 그대로 남는다.

## 플랫폼 비교

| 방식                                                | 장점                                                                                                  | 단점                                                                   |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| A. Cloudflare Workers + D1 + R2 (+ Durable Objects) | 기존 계정·도메인·wrangler를 그대로 쓴다. 무료 한도가 넓다. `domain.mjs`를 Worker에서 재사용할 수 있다 | 인증을 직접 만든다. D1은 단일 리전 SQLite라 복잡한 쿼리에 제약         |
| B. Supabase (Postgres + Auth + Realtime + Storage)  | 로그인·실시간·파일 저장이 바로 제공된다. 커뮤니티까지 가장 빨리 도달한다                              | 서비스 하나 더 운영. Row Level Security 정책을 잘못 쓰면 데이터가 샌다 |
| C. 직접 운영 (Node + Postgres, VPS)                 | 제약 없음                                                                                             | 서버 관리·백업·보안 패치를 혼자 맡는다                                 |

**결정: B.** 처음에는 A를 추천했으나 직접 운영하는 API 서버 없이 가는 쪽으로 바꿨다. 이 설계에서 서버가 하는 일은 로그인과 변경 로그 저장뿐이라 Supabase Auth와 RLS가 걸린 테이블 하나로 끝난다. 인증 코드 발송·세션 갱신·요청 제한을 만들지 않아도 된다. 실시간이 필요해지면 Supabase Realtime을 쓴다.

감수하는 것: 무료 프로젝트는 7일 비활동 시 일시 정지되고 백업이 없다. 실사용자가 생기면 Pro(월 25달러)로 올린다. 내장 메일 발송은 시간당 몇 통이라 실배포에는 Resend SMTP를 연결한다.

서버 쪽 코드는 이 저장소의 `supabase/` 디렉터리에 SQL 마이그레이션과 Auth 설정으로 둔다. 입력 검증은 `domain.mjs`의 같은 함수를 받는 쪽 앱이 실행한다.

## 인증

| 방식               | 앱 안에서의 흐름                                               | 비고                                                |
| ------------------ | -------------------------------------------------------------- | --------------------------------------------------- |
| 이메일 인증 코드   | 이메일 입력 → 6자리 코드 수신 → 입력. 브라우저로 나가지 않는다 | 발송 서비스(Resend 등) 필요. 가장 단순              |
| Sign in with Apple | 외부 브라우저 → 사이트 콜백 → 커스텀 URL 스킴으로 복귀         | App Store 밖 배포라 의무는 아니다. 설정 항목이 많다 |
| GitHub OAuth       | 위와 같은 브라우저 왕복                                        | 개발자 외 사용자에게 맞지 않는다                    |

**추천: 이메일 인증 코드로 시작.** Supabase Auth의 이메일 OTP를 그대로 쓴다. Apple 로그인은 iOS나 App Store 배포를 할 때 추가한다.

- 세션(JWT + refresh token)은 supabase-js가 관리한다. 앱은 Electron `safeStorage`로 암호화해 `userData`에 저장한다. 렌더러에는 주지 않는다.
- 요청은 메인 프로세스에서 보낸다. 렌더러 CSP는 바꾸지 않는다.
- 프로젝트 URL과 anon key는 메인 코드에 고정한다. 테스트용 재정의는 업데이트 피드와 같은 규칙으로 `127.0.0.1` origin만 허용한다.
- 코드 발송 횟수 제한은 Supabase Auth 설정을 쓴다.

## 동기화 설계

### 방식 비교

| 방식                 | 내용                                                         | 장점                                                                    | 단점                                                                    |
| -------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| A. 스냅샷            | 전체 상태 JSON을 올리고 내려받는다. 최신 저장이 이긴다       | 구현이 가장 단순                                                        | 두 기기에서 번갈아 쓰면 한쪽 변경이 통째로 사라진다. 백업 용도로만 적합 |
| B. 행 단위 변경 로그 | 바뀐 행을 로그로 쌓아 교환한다. 같은 행은 늦은 변경이 이긴다 | 지금 저장 구조(행 단위 diff)와 맞는다. 기록은 추가만 하므로 충돌이 없다 | 로컬 스키마 변경 필요. 순서(`position`) 충돌은 완벽하지 않다            |
| C. CRDT 라이브러리   | Yjs·Automerge로 문서를 통째로 병합                           | 충돌 처리가 자동                                                        | 데이터 모델과 저장 구조를 바꿔야 한다. 의존성이 크다                    |

**추천: B.** `storage.mjs`가 이미 행 단위로 변경을 찾아낸다. 그 지점에서 변경 로그를 함께 쓰면 도메인 리듀서와 렌더러는 거의 바꾸지 않아도 된다.

### 대상과 규칙

| 데이터             | 동기화       | 규칙                                                                 |
| ------------------ | ------------ | -------------------------------------------------------------------- |
| `projects`         | 예           | 행 단위 늦은 변경 우선. 삭제는 tombstone                             |
| `tasks`            | 예           | 같음. `position`도 늦은 변경 우선. 동시에 순서를 바꾸면 섞일 수 있다 |
| `focus_records`    | 예           | 추가만 한다. 안정적인 ID로 중복 없이 합친다                          |
| `settings`         | 예           | 단일 행 늦은 변경 우선                                               |
| `timer`            | 아니오       | 실행 중인 타이머는 기기에 속한다                                     |
| 3초 클립·영상 편지 | 아니오 (1차) | 용량이 크고 얼굴 영상이다. 필요하면 별도 단계에서 선택 업로드        |

### 로컬 스키마 변경 (`SCHEMA_VERSION` 2)

- `focus_records.id`를 정수 인덱스에서 안정적인 문자열 ID로 바꾼다. `settleTimer`가 기록을 만들 때 ID를 생성하고 `normalizeState`가 없는 ID를 채운다. `FocusRecord` 타입에 `id`가 추가된다.
- `projects`·`tasks`·`focus_records`·`settings`에 `updated_at`(하이브리드 논리 시계)과 `deleted_at`을 둔다. 삭제한 행은 바로 지우지 않고 tombstone으로 남겼다가 서버 확인 뒤 정리한다.
- `changes` 테이블: `seq, entity, id, data, hlc, device_id, pushed`. `writeChanges`가 바뀐 행마다 한 줄씩 쓴다.
- `sync_state` 테이블: `device_id, cursor`(서버에서 마지막으로 받은 위치).
- 상태 객체(`AppState`)의 모양은 유지한다. `updated_at`과 tombstone은 SQLite에만 있고 렌더러로 가지 않는다.

이 변경은 서버 없이 먼저 배포할 수 있다. 이후 어떤 순서로 가더라도 필요하다.

### 교환 흐름

```
[앱 A] 변경 → SQLite 행 갱신 + changes 추가
       ─ push: pushed=0인 changes를 POST /sync/changes ─▶ [서버] server_seq 부여, 저장
       ◀ pull: GET /sync/changes?since=cursor ───────────  [서버] 다른 기기의 변경 반환
       받은 변경을 hlc 비교로 적용 → 상태 다시 읽기 → 기존 subscribe 경로로 렌더러에 전달
```

- 주기: 로컬 변경 직후 push, 앱 실행 시와 5분마다 pull. 실패하면 조용히 다음 주기에 재시도한다.
- 첫 로그인 때 서버가 비어 있으면 로컬 전체를 올린다. 서버에 데이터가 있으면 ID 기준으로 합친다. 첫 실행 예시 데이터(`t1`~`t5`, `p1`~`p3`)는 두 기기가 같은 ID를 쓰므로 하나로 합쳐진다.
- 받는 쪽 앱이 원격 행을 `domain.mjs`의 검증 함수로 확인한 뒤 적용한다. 검증 함수는 지금 내부 함수라 export가 필요하다. 서버에는 크기·형식 CHECK 제약만 둔다.
- JSON 가져오기는 동기화를 켠 상태에서는 전체 교체가 아니라 변경 로그로 기록해야 한다. 기존 행은 tombstone, 가져온 행은 추가로 처리하는 방식과 동기화 중 가져오기를 막는 방식 중 하나를 고른다.

## 커뮤니티 기능

### 후보와 단계

| 단계 | 기능                | 내용                                                                      | 필요 요소                       |
| ---- | ------------------- | ------------------------------------------------------------------------- | ------------------------------- |
| 1    | 기록 공유           | 앱이 날짜별 포모도로 수와 집중 시간을 서버에 올린다. 제목은 올리지 않는다 | 계정, `daily_stats`             |
| 2    | 그룹                | 초대 코드로 그룹을 만들고 참여한다. 구성원의 오늘·이번 주 합계를 본다     | `groups`, `group_members`       |
| 3    | 실시간 함께 집중    | 그룹 안에서 지금 집중 중인 사람 수와 상태를 본다                          | Durable Objects, WebSocket      |
| 4    | 클립·영상 편지 공유 | 3초 클립이나 주간 영상을 그룹에 공유한다                                  | R2 업로드, 보존 기간, 삭제 전파 |

**추천: 1과 2를 1차 범위로.** 공개 피드와 검색은 두지 않는다. 그룹은 초대 코드로만 들어오므로 모더레이션 범위가 작다. 4는 얼굴 영상이라 가장 민감하다. 하더라도 마지막에 하고 클립마다 개별 선택으로만 공유한다.

### 공유 데이터 모델

`daily_stats`는 클라이언트가 `focus_records`에서 계산해 올린다. 기기별로 올리고 서버가 사용자·날짜로 합산한다. 동기화를 켜지 않은 두 기기도 합계가 맞는다.

| 열              | 내용                          |
| --------------- | ----------------------------- |
| `user_id`       |                               |
| `device_id`     | 기기별 합산 단위              |
| `date`          | 기기 현지 날짜 `YYYY-MM-DD`   |
| `pomodoros`     | 반올림 포모도로 합 (0.5 단위) |
| `focus_seconds` | 실제 집중 초 합               |
| `completed`     | 1포모도로를 채운 기록 수      |
| `updated_at`    |                               |

그룹 화면이 보여주는 것: 구성원별 오늘 포모도로 수, 이번 주 합, 마지막 기록 시각. 작업 이름과 프로젝트는 없다.

### 프라이버시와 운영

- 그룹에 공개되는 사용자 정보는 표시 이름 하나다. 이메일은 노출하지 않는다.
- 그룹 나가기와 그룹 삭제를 둔다. 나가면 그 그룹에서 통계가 바로 사라진다.
- 신고·차단은 그룹 단위 강퇴(그룹 생성자)로 시작한다. 공개 피드가 없으므로 그 이상은 1차에서 만들지 않는다.
- 이메일을 수집하므로 사이트에 개인정보 처리방침 페이지가 필요하다. 문구는 사용자가 작성한다.
- 탈퇴: `DELETE /me`로 사용자·기기·변경 로그·통계·그룹 소속·R2 객체를 전부 지운다.

## 서버 데이터 모델 (Supabase Postgres)

1단계는 `devices`와 `changes` 두 테이블과 RPC 함수 세 개다. 상세 DDL은 `sync-design.md`.

```
auth.users     Supabase Auth가 관리. 이메일, 생성 시각
devices        user_id, id, name, created_at, last_sync_at
changes        server_seq, user_id, device_id, entity, id, data, hlc, created_at   (추가만 가능)
daily_stats    user_id, device_id, date, pomodoros, focus_seconds, completed, updated_at   (2단계)
groups         id, name, invite_code(unique), owner_id, created_at                 (2단계)
group_members  group_id, user_id, display_name, joined_at                          (2단계)
shared_clips   id, user_id, group_id, storage_path, duration, at, created_at, deleted_at   (4단계. Supabase Storage)
```

모든 테이블은 RLS로 `auth.uid()` 기준 접근만 허용한다. 그룹 합계처럼 다른 사용자 행을 읽어야 하는 조회는 `security definer` 함수로 노출한다.

## API 초안

별도 HTTP API를 만들지 않는다. 앱은 supabase-js로 Auth와 테이블·RPC를 직접 호출한다.

| 동작                        | 호출                                                                   |
| --------------------------- | ---------------------------------------------------------------------- |
| 인증 코드 발송·확인         | `auth.signInWithOtp` / `auth.verifyOtp`                                |
| 로그아웃·탈퇴               | `auth.signOut` / `rpc('delete_my_account')`                            |
| 변경 로그 push·pull         | `from('changes').insert` / `rpc('pull_changes')`                       |
| 통계 올리기 (2단계)         | `from('daily_stats').upsert`                                           |
| 그룹 생성·참여·조회 (2단계) | `from('groups').insert` / `rpc('join_group')` / `rpc('group_summary')` |

## 앱 측 변경

| 영역                       | 내용                                                                                             |
| -------------------------- | ------------------------------------------------------------------------------------------------ |
| `electron/storage.mjs`     | 스키마 v2 마이그레이션, 변경 로그 기록, 원격 변경 적용                                           |

## 운영과 비용

| 항목 | 내용                                                                                                            |
| ---- | --------------------------------------------------------------------------------------------------------------- |
| 배포 | `supabase db push`로 마이그레이션 적용. Auth 설정은 대시보드 또는 `config.toml`                                 |
| 비밀 | `service_role` 키는 어디에도 저장하지 않는다. anon key는 공개 값. Resend SMTP 자격 증명은 Supabase 대시보드에만 |
| 비용 | 무료 플랜으로 시작. 7일 비활동 시 일시 정지. 실사용자가 생기면 Pro(월 25달러)                                   |
| 백업 | 무료 플랜 없음. Pro는 일일 백업. 그 전까지는 앱의 로컬 데이터가 원본이다                                        |
| 관측 | Supabase 대시보드의 Auth·Postgres 로그. 앱 쪽 로그에 사용자 식별 정보를 남기지 않는다                           |

## 단계 제안

두 순서가 가능하다. 0단계는 공통이다.

| 단계 | 순서 1 (동기화 우선)                          | 순서 2 (커뮤니티 우선)  |
| ---- | --------------------------------------------- | ----------------------- |
| 0    | 로컬 스키마 v2 (기록 ID, updated_at, changes) | 같음                    |
| 1    | 계정 + 변경 로그 동기화                       | 계정 + 일별 통계 + 그룹 |
| 2    | 그룹 + 일별 통계                              | 변경 로그 동기화        |
| 3    | 실시간 함께 집중                              | 같음                    |
| 4    | 클립 공유                                     | 같음                    |

**추천: 순서 2.** 동기화는 로컬 데이터를 건드리므로 실수하면 유실로 이어진다. 통계 공유는 읽기 전용 파생 데이터라 로컬에 영향이 없고 서버·인증·배포 기반을 같은 비용으로 만든다. 다만 서버를 붙이는 첫 이유가 "기기를 바꿔도 데이터를 잃지 않게"라면 순서 1이 맞다.

## 결정할 항목

1. 첫 목적: 기기 간 동기화인가 다른 사람과의 공유인가. (추천: 공유 먼저)
2. 플랫폼: Cloudflare Workers + D1인가 Supabase인가. (처음 추천 Cloudflare → Supabase로 결정)
3. 로그인: 이메일 인증 코드로 시작하는가. (추천: 예)
4. 1차 커뮤니티 범위: 초대 코드 그룹 + 일별 포모도로 수·집중 시간. 공개 피드 없음. (추천: 이대로)
5. 공유 항목: 포모도로 수와 집중 시간만인가 작업 제목도 포함하는가. (추천: 수와 시간만)
6. 클립·영상 편지 공유: 범위에 넣는가. (추천: 1차 제외)
7. 브라우저 미리보기: 서버 기능 제외. (추천: 제외)
8. 그룹 화면 위치: 왼쪽 내비게이션 탭인가 설정 안인가.
9. 동기화 중 JSON 가져오기: 변경 로그로 바꾸는가 막는가.
10. 서버 코드 위치: 이 저장소 `supabase/`인가 별도 프로젝트인가. (추천: `supabase/`)
11. 사이트에 개인정보 처리방침·이용약관 페이지 추가. 문구는 사용자 작성.

## 결정 사항 (2026-10-20 확정)

1. 첫 목적은 기기 간 동기화다. 순서 1로 진행한다.
2. 플랫폼은 Supabase(Auth + Postgres + RLS). 직접 운영하는 API 서버는 두지 않는다. SQL 마이그레이션과 설정은 이 저장소의 `supabase/`에 둔다. 처음 결정은 Cloudflare Workers였으나 같은 날 바꿨다.
3. 로그인은 이메일 인증 코드로 시작한다.
4. 1차 커뮤니티 범위는 초대 코드 그룹과 일별 포모도로 수·집중 시간. 공개 피드는 없다. 작업 제목은 공유하지 않는다.
5. 클립·영상 편지 공유는 1차에서 제외한다.
6. 브라우저 미리보기는 서버 기능을 지원하지 않는다.
7. 동기화 중 JSON 가져오기는 막지 않고 변경 로그로 기록한다. 상세는 `sync-design.md`.
8. 그룹 화면 위치는 2단계 상세 설계에서 정한다.
9. 개인정보 처리방침·이용약관 페이지는 1단계 배포 전에 사이트에 추가한다. 문구는 사용자가 작성한다.
