# To3mato 선택형 Supabase 실시간 동기화 계획

작성일: 2026-10-26
상태: 승인된 계획의 앱·서버 코드 구현 및 로컬 통합 검증 완료. 운영 프로젝트 연결과 SQL·서버 함수 배포 및 권한 검증 완료. 실제 이메일 로그인과 계정 간 실서버 동기화 종합 검증은 남아 있다. 구성 절차와 검증 경계는 `supabase-sync-operations.md`를 따른다.

이 문서는 `sync-design.md`와 `server-community-design.md`의 동기화 범위·전송 방식·플랫폼 제한을 대체한다. 기존 문서의 구현 기록은 유지한다. 제품 기준은 `product-plan.md`를 따른다.

## 1. 요구사항과 권장 기본값

사용자가 요청한 확정 범위:

- 연동은 선택이다. 선택하지 않으면 계정과 네트워크 없이 기존 기능을 쓴다.
- 연동을 켜면 타이머, 할 일, 프로젝트가 실시간으로 반영된다.
- 기록, 설정, 부가 기능까지 거의 모든 사용자 데이터를 연동한다.
- 다른 플랫폼으로 출시해도 같은 계정과 데이터를 사용할 수 있어야 한다.

아래 정책은 2026-10-26 사용자의 “그대로 구현” 지시로 확정했다. 추가 선택 항목과 카피 결정은 11절에 기록한다.

- 연동 활성화는 기기별로 선택한다. 로그인만으로 업로드를 시작하지 않는다.
- 연결된 기기의 온라인 타이머는 계정당 하나다. 어느 기기에서든 이어서 조작한다.
- 일시적인 오프라인에서도 작업을 계속한다. 재연결 시 변경을 병합한다.
- 이미지와 영상도 최종 연동 범위에 포함한다. 최초 활성화 흐름에서 파일 업로드 범위를 확인할 수 있게 한다.
- 연동 해제는 해당 기기의 송수신 중단이다. 서버 데이터 삭제와 구분한다.
- 구현 순서는 나누되 타이머와 미디어를 범위에서 영구 제외하지 않는다.

아래 구현은 확정한 정책을 따른다. 운영 프로젝트 연결과 플랫폼별 출시는 별도 작업이다.

`sync-design.md`의 승인 문구 중 아래는 의미가 바뀌어 그대로 재사용하지 않는다. 대체 문구는 11절의 사용자 승인 결과를 반영했다.

- `로그인하면 할 일과 집중 기록을 같은 계정의 다른 Mac과 동기화합니다.` 로그인만으로 업로드하지 않고, Mac 전용이 아니며, 동기화 범위가 기록과 할 일보다 넓다.
- `로그인 상태이므로 가져온 데이터가 같은 계정의 다른 Mac에도 적용됩니다.` Mac 전용 표현이고 7절의 가져오기 규칙에 따라 적용 범위가 달라진다.
- 계정 삭제 대화상자의 `서버에 저장된 계정과 동기화 데이터를 삭제합니다.` / `이 컴퓨터의 데이터는 남습니다.` 8절의 서버 데이터 삭제 동작과 범위(파일 포함)가 일치하는지 확인한 뒤 재사용 여부를 정한다.

버튼, 입력 레이블, 오류 줄처럼 의미가 바뀌지 않은 문구는 그대로 쓴다.

## 3. 동기화 범위

| 대상 | 동기화할 내용 | 처리 |
| --- | --- | --- |
| 타이머 | 실행할 일, 집중·체크인·휴식 단계, 시작·정지·재개·전환·종료, 누적 시간 | 공유 세션과 서버 명령 |
| 할 일 | 제목, 예상량, 남은 분량, 후속 작업 관계, 프로젝트, 날짜, 완료, 순서, 삭제 | 변경 직후 반영 |
| 프로젝트 | 이름, 아이콘, 색상, 결과, 표지 이미지, 순서, 삭제 | 변경 직후 반영. 이미지 파일은 별도 전송 |
| 집중 기록 | 실제 집중 시간, 포모도로, 연결 작업, 기록 시각 | 세션 기준 중복 없는 정산 |
| 완료 티켓·다이어리 | 메모, 강조, 스티커, 무효화, 완료 당시 정보, 클립 연결 | 티켓 동기화 후 다이어리 재계산 |
| 템플릿 | 이름, 단계, 단계별 예상량, 삭제 | 변경 직후 반영 |
| 계획·캘린더·회고 | 작업 날짜와 순서, 일일 용량, 계획·회고 완료 상태 | 원본 데이터 동기화 후 화면 재계산 |
| 사용자 설정 | 집중·휴식 길이, 하루 용량, 계획·회고 시각, 요일 | 항목별 병합 |
| 클립·주간 영상 | 원본, 썸네일, 메타데이터, 생성·읽음 상태, 삭제 | 메타데이터 즉시 반영, 파일은 비동기 전송 |
| 통계·성장 화면 | 집중 기록과 설정으로 계산되는 진척·시각화 | 원본을 동기화하고 공통 규칙으로 계산 |
| 기기 설정 | 트레이 모양, 창 위치, 알림·카메라 권한, 로컬 경로, 다운로드 캐시 | 기기에 보관 |

현재 작업 트리의 숲 시각화는 기록에서 계산된다. 이 기능은 아직 `main`에 합치지 않은 `feature/tomato-growth` 브랜치에 있으므로 동기화 범위는 합친 뒤의 구현을 기준으로 다시 확인한다. 구현 확정 시 같은 원본과 같은 계산 버전에서 같은 결과가 나오도록 검증한다. 향후 사용자가 직접 배치하는 기능이 추가되면 배치 데이터도 동기화 대상이다.

일시적인 화면 상태(열린 탭, 스크롤, 팝업 표시)는 공유하지 않는다. 운영체제 알림의 발송 이력은 기기별로 유지하되 계획·회고 완료 여부는 공유한다. 다른 기기에서 완료한 일을 다시 요청하는 알림은 취소한다.

## 4. 구성과 플랫폼 경계

```text
화면 → 공통 명령·도메인 → 로컬 저장 + 미전송 명령 큐
                              ↕ 공통 동기화 엔진
                         Supabase Auth
                         Postgres + RPC
                         Realtime private channel
                         Storage private bucket
```

- 도메인 규칙과 동기화 프로토콜을 Electron과 분리한다. 웹·모바일도 같은 명령·데이터 계약을 사용한다.
- 데스크톱은 메인 프로세스에서 SQLite, 인증, 네트워크를 담당한다. 렌더러에는 필요한 상태와 제한된 명령만 제공한다.
- 웹은 IndexedDB, 모바일은 해당 플랫폼의 로컬 DB와 보안 저장소를 붙인다. 웹·모바일 프레임워크 선택은 이번 계획에서 고정하지 않는다.
- 공통 인터페이스: `LocalRepository`, `SyncTransport`, `SessionStore`, `AssetStore`, `Clock`, `NotificationAdapter`.
- DB 저장과 미전송 명령 등록은 같은 로컬 트랜잭션에서 처리한다. 파일은 별도 재시도 큐를 둔다.
- Electron 파일 경로·IPC·Node 전용 API가 서버 데이터나 공통 엔진으로 새지 않게 한다.
- 다른 플랫폼 출시 자체는 별도 작업이다. 이번 구현에서 Mac 두 인스턴스와 브라우저 시험 클라이언트로 프로토콜 재사용을 검증한다.

Supabase 역할은 Auth(로그인), Postgres(확정 상태와 변경 이력), Realtime(변경 알림), Storage(파일)로 나눈다. 별도 상시 API 서버 없이 SQL RPC를 사용한다. 계정 및 파일 삭제 같은 관리자 작업이 필요하면 제한된 Edge Function을 둔다.

## 5. 실시간 전송과 복구

1. 로컬 작업을 즉시 저장하고 화면에 반영한다. 아직 확정되지 않은 명령은 큐에 남긴다.
2. 연결 상태이면 일반 변경을 짧게 묶어 RPC로 보낸다. 타이머 조작은 즉시 보낸다.
3. 서버는 인증 사용자, 입력 값, 관계, 명령 ID, 기준 버전을 검증한다. 확정 상태와 변경 이력을 한 트랜잭션에 기록한다.
4. 커밋된 변경을 계정별 비공개 Realtime 채널로 알린다.
5. 수신 기기는 마지막 cursor 이후 변경을 가져와 확정 상태와 cursor를 함께 저장한 뒤 미전송 로컬 명령을 다시 적용한다.

Realtime은 빠르게 변경을 알리는 통로다. 영구 기록과 누락 복구의 기준은 Postgres의 변경 이력이다. 이벤트 중복·역순·유실을 허용하고 결과가 수렴하도록 만든다. Supabase는 DB 변경 구독에 Broadcast를 권장하므로 private Broadcast를 기본안으로 사용한다. [공식 문서](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes)

- 최초 연결은 구독을 시작하고 일관된 snapshot과 cursor를 받은 뒤 그 이후 변경을 재조회한다. 구독 준비 중 변경도 빠뜨리지 않는다.
- 재접속·앱 재개·인증 갱신 후 항상 cursor로 재조회한다. 연결 중에도 낮은 빈도의 정합성 확인을 둔다.
- 동일한 `operation_id` 재전송은 이전 처리 결과를 반환한다. 응답 유실 때문에 같은 작업을 두 번 만들지 않는다.
- 기존 설계의 identity 순번과 5초 지연은 커밋 순서를 보장하지 못한다. 계정별 동기화 상태 행을 잠근 뒤 트랜잭션 안에서 revision을 증가시킨다. 같은 계정의 쓰기는 이 잠금 규칙을 반드시 거친다.
- snapshot의 상태와 cursor는 같은 DB snapshot에서 읽는다. cursor는 계정·서버 epoch와 묶고 bigint는 전송 시 문자열로 표현한다.
- 이력 정리 또는 서버 복구로 cursor가 무효가 되면 전체 snapshot을 다시 받는다. 미전송 명령은 별도로 보존한다. 단순히 서버 최댓값이 작아졌는지만으로 복구를 판정하지 않는다.
- 모르는 데이터 버전이나 잘못된 변경은 조용히 건너뛰고 cursor를 진행하지 않는다. 격리·재시도 또는 호환 버전 요구 상태로 전환한다.

온라인·전경·안정된 네트워크의 시험 환경에서 일반 변경 반영 p95 1초 이내를 목표로 한다. 보장된 서비스 수치가 아니라 구현 후 측정할 목표다. 파일 전송 시간과 OS가 중지한 앱은 별도로 측정한다.

## 6. 공유 타이머

### 상태와 시간 계산

권장 필드: `user_id`, `session_id`, `task_id`, `phase`, `status`, `duration_ms`, `accumulated_ms`, `started_at`, `revision`, `last_controller_device_id`.

- 한 계정의 활성 타이머는 최대 하나다. 기기마다 동일한 세션을 표시한다.
- 매초 서버를 갱신하지 않는다. 시작·일시정지·재개·작업 전환·종료·체크인 때 상태를 저장한다.
- 실행 중 경과 시간은 누적 시간과 서버 기준 시작 시각으로 계산한다. 서버 시간 응답으로 기기 시계 차이를 보정하고 표시 사이에는 단조 시계를 사용한다.
- 기기 절전·앱 종료 동안에도 시작 시각 기준으로 경과한다. 복귀할 때 서버 상태를 읽고 다시 계산한다.
- 집중 완료는 현재 제품처럼 체크인으로 넘어간다. 체크인 응답 전 휴식을 자동 시작하지 않는다.

### 여러 기기의 동시 조작

- 모든 타이머 명령에 `operation_id`, `session_id`, `expected_revision`을 보낸다.
- 서버는 계정 잠금 아래에서 현재 revision과 비교해 명령을 적용한다. 오래된 명령은 최신 상태와 충돌 결과를 반환한다. 다른 기기의 새 타이머를 과거 명령으로 덮지 않는다.
- 할 일 변경과 타이머 정산이 연결되는 작업(집중 중 작업 삭제·완료, 작업 전환, 체크인)은 하나의 서버 트랜잭션으로 처리한다.
- 정산은 세션별 고유 키로 중복을 막는다. 종료된 같은 세션에 여러 기기가 완료 요청을 보내도 집중 기록은 하나다. 티켓과 후속 작업 생성도 같은 명령에 대해 한 번만 발생한다.
- 현재 `settleTimer()`의 무작위 ID와 `applyRemote()`의 기기별 정산을 공유 모드에서 그대로 호출하지 않는다. 로컬 전용 경로는 유지하고 공유 모드는 확정 결과를 적용한다.
- 서버 확정 상태와 로컬의 임시 표시를 분리한다. 충돌 시 실제 확정 상태로 복구하며 발생한 로컬 작업을 조용히 버리지 않는다.

### 종료 처리와 기기 부가 동작

- 기기는 종료 예정 시각에 완료 RPC를 요청한다. 모든 앱이 닫혀 있으면 다음 접속 때 같은 RPC로 정산한다. 기록 종료 시각은 다음 접속 시각이 아니라 세션의 예정 종료 시각이다.
- 별도 서버 스케줄러 없이도 재접속 시 결과가 정확해야 한다. 앱이 모두 종료된 상태의 서버 푸시 알림은 별도 범위다.
- 일시정지 상태로 모든 앱이 닫히면 예정 종료 시각이 없다. 권장안은 자동 정산하지 않고 일시정지 세션을 유지하는 것이다. 다음 접속에서 사용자가 재개하거나 종료한다. 오래된 일시정지 세션을 자동으로 종료할지와 그 기한은 11절의 결정 항목이다.
- 소리·완료 알림·촬영 요청은 기본적으로 마지막으로 조작한 기기에서 발생시킨다. 다른 기기는 상태만 반영한다. 기기별 권한 제한은 유지한다.
- `completedMoment()`처럼 배열 길이 증가를 새 완료로 판단하는 코드는 세션 ID와 처리 기기 정보를 사용하도록 바꾼다. 원격 기록 수신으로 촬영창이 여러 번 뜨지 않아야 한다.

### 오프라인 한계와 처리

서로 통신하지 못하는 두 기기에서 계정당 하나의 타이머를 강제하면서 양쪽 실행도 허용하는 것은 불가능하다. 온라인 공유 세션과 오프라인 임시 실행을 구분한다.

- 연결이 끊긴 기기의 타이머와 조작 이력을 로컬에 보존한다. 진행 중 실행을 네트워크 오류 때문에 중단하지 않는다.
- 재연결 시 같은 세션·같은 기준 revision의 명령은 한 번만 적용한다.
- 다른 기기에서 세션을 변경했으면 과거의 시작·정지 명령을 현재 타이머에 자동 재생하지 않는다.
- 이미 서버에서 정산한 세션의 사본은 중복 기록으로 추가하지 않는다.
- 오프라인에서 별도로 실행한 세션은 보존한다. 기존 확정 세션과 시간이 겹치면 자동 이중 집계하지 않고 해결 대기 기록으로 남긴다. 기록 선택·별도 보존 동작과 필요한 문구는 구현 단계에서 검토한다.

## 7. 데이터 병합과 서버 모델

| 데이터 | 권장 병합 규칙 |
| --- | --- |
| 할 일·프로젝트·티켓·설정 | 변경된 필드만 전송. 다른 필드 수정은 함께 유지. 같은 필드 동시 수정은 서버가 수락한 revision 순서로 정하고 덮인 값은 변경 이력에 보존 |
| 순서 | 목록 단위 이동 명령과 기준 revision으로 처리. 충돌 시 최신 목록에 재적용. 수신 때마다 전체 position을 다시 써서 전송하는 루프 제거 |
| 삭제 | 삭제 표식을 전파. 오래된 수정으로 자동 복원하지 않음. 명시적 복원만 허용 |
| 집중 기록 | 세션별 중복 방지. 과거 가져온 기록은 기존 안정 ID 유지 |
| 계획·회고 완료 | `(사용자, 날짜, 종류)`별 완료 데이터. 알림 발송 이력과 분리 |
| 미디어 | 변경 불가능한 asset 버전과 참조. 파일 교체는 새 객체 생성 |

기존 HLC와 변경 로그는 이전 데이터와 로컬 변경 파악에 활용한다. 공유 타이머에는 HLC의 마지막 쓰기 우선 규칙을 적용하지 않는다. 일반 필드의 승자도 기기 벽시계가 아니라 서버 확정 revision으로 정한다.

서버 테이블 초안:

- `devices`, `account_sync_state`, `processed_operations`, `sync_changes`.
- `projects`, `tasks`, `focus_records`, `tickets`, `templates`, `user_settings`, `ritual_completions`.
- `timer_sessions`와 계정별 활성 세션 참조.
- `assets`, `clips`, `deliveries`와 필요 시 충돌 보관 테이블.

모든 사용자 데이터의 소유자는 `user_id`다. 관계도 같은 사용자 안에서만 연결되도록 복합 키 또는 서버 검증을 둔다. 기존 문자열 ID와 legacy 기록 ID를 수용한다. 새 ID는 UUID로 발급하되 모든 기존 ID를 UUID로 강제 변환하지 않는다.

클라이언트가 테이블에 임의로 쓰면서 검증·revision·로그를 우회하지 못하게 한다. 쓰기 RPC에서 입력 크기, 값 범위, 관계, 소유권을 검증한다. RLS는 사용자 격리, RPC는 업무 규칙을 담당한다. 타이머·체크인 규칙의 JS와 SQL 구현은 같은 시나리오 자료로 검증한다.

JSON 가져오기는 연동 중에도 막지 않되 파일 내용을 전체 상태로 덧쓰지 않는다. 권장안은 가져오기를 추가·갱신 명령으로만 변환하고, 파일에 없는 행을 삭제로 전파하지 않는 것이다. 현재 `save()`의 동작을 연동 중에 그대로 쓰면 한 기기의 가져오기가 모든 기기의 데이터를 지운다. 연동을 끈 기기의 가져오기는 기존 동작을 유지한다. 가져오기 안내 문구는 사용자 요청으로 제거했다. JSON 내보내기는 데이터만 포함한다.

삭제 표식과 멱등 처리 키의 보존 기간은 snapshot 정책과 함께 정한다. 현재 `load()`의 30일 정리는 이 정책으로 교체한다. 오래된 기기는 전체 재동기화 후 미전송 명령을 재검증한다. 단순히 30일 후 표식을 지워 삭제 데이터가 살아나는 방식은 사용하지 않는다.

날짜만 있는 계획은 `YYYY-MM-DD`로 유지한다. 사건 시각은 UTC로 저장한다. 주간 묶음과 회고 기준은 계정의 IANA 시간대를 사용하도록 추가한다. 여행이나 기기 시간대 변경으로 영상 배달·주간 기록 ID가 달라지지 않게 한다.

## 8. 선택형 연동의 생명주기

1. 기본값은 연동 꺼짐이다. Supabase 세션·구독·업로드를 자동 생성하지 않는다. 기존 앱 업데이트 확인과는 별개다.
2. 사용자가 로그인하고 이 기기의 연동을 선택한다. 업로드되는 데이터와 파일 범위를 제시한다. 새 안내 문구는 별도 승인 후 넣는다.
3. 최초 연결 전 SQLite, 영상·이미지 저장소, 기타 로컬 상태의 복구 지점을 만든다. 기존 JSON 내보내기만으로 미디어까지 백업됐다고 간주하지 않는다.
4. 서버 snapshot과 로컬 데이터를 비교한다. 동일 ID는 병합하고 다른 ID는 보존한다. 같은 제목만으로 중복 삭제하지 않는다. 활성 타이머는 자동 덮어쓰지 않고 공유 세션으로 채택할 대상을 명확히 한다.
5. 연동 해제는 구독과 작업 큐 실행을 중단한다. 이미 서버가 수락한 요청은 되돌릴 수 없으므로 종료 상태를 기록한다. 이후 로컬 변경을 원래 계정에 귀속된 분기 이력으로 보존한다.
6. 같은 계정으로 다시 켜면 해제 이후 변경과 서버 변경을 병합한다. `resetSync()`로 모든 행을 최신 변경처럼 재업로드하지 않는다.
7. 로그아웃과 인증 만료를 구분한다. 인증 만료는 동기화만 멈추고 큐를 유지한다. 명시적 로그아웃은 토큰을 삭제하되 계정 데이터·큐를 계정별 저장소에 보존하고 다른 계정에 노출하거나 보내지 않는다.
8. 다른 계정으로 로그인하면 별도 저장 영역을 연다. 기존 계정 또는 로컬 전용 데이터를 자동 업로드하지 않는다. 별도 가져오기 동작으로만 복사한다.
9. 서버 데이터 삭제·탈퇴는 연동 해제와 별도 동작이다. DB와 Storage를 모두 삭제하고 작업 완료를 확인한다. Auth 행 삭제만으로 파일 삭제까지 끝났다고 보지 않는다.

## 9. 파일과 보안

- 프로젝트 이미지·클립·영상은 비공개 Storage bucket에 저장한다. 경로는 사용자와 asset ID에 귀속시키고 로컬 절대 경로를 전송하지 않는다.
- `assets`에는 소유자, 객체 경로, MIME, 크기, 해시, 상태를 둔다. 업로드가 확인된 후 다른 기기가 다운로드 가능한 상태로 전환한다.
- 메타데이터와 객체 업로드는 하나의 DB 트랜잭션이 아니므로 준비·완료·실패 상태와 재시도, 고아 파일 정리를 구현한다.
- 새 기기는 메타데이터부터 받고 파일은 필요할 때 캐시한다. 로컬에 아직 없는 파일도 재연결 후 받을 수 있어야 한다.
- 주간 영상 생성은 계정·주간·생성 버전 키로 중복 게시를 막는다. 플랫폼별 코덱 차이와 기존 WebM 재생 가능 여부를 시험하고 필요하면 공통 재생 형식으로 변환한다.
- 삭제된 파일의 재업로드를 막도록 객체 삭제와 메타데이터 삭제 표식을 조정한다. 업로드 크기·재시도·동시 전송·보관량 제한은 운영 설정으로 관리한다.
- DB의 RLS, Realtime의 채널 권한, Storage의 객체 권한을 각각 설정한다. 사용자 A가 사용자 B의 행·채널·파일에 접근하는 시험을 별도로 둔다. [DB RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Realtime 권한](https://supabase.com/docs/guides/realtime/authorization), [Storage 권한](https://supabase.com/docs/guides/storage/security/access-control)
- 앱에는 publishable key만 포함한다. 관리자 secret key는 앱에 넣지 않는다. 레거시 anon 키는 2026년 말 폐기 예정이므로 쓰지 않는다. 데스크톱 세션은 OS 보안 저장소를 이용하고 렌더러에 전달하지 않는다. [API 키](https://supabase.com/docs/guides/getting-started/api-keys)
- 브라우저 시험 클라이언트는 OS 보안 저장소가 없어 세션을 브라우저 저장소에 둔다. 이 클라이언트는 프로토콜 검증 전용이며 공개 배포하지 않는다. 웹 출시 때의 세션 저장 방식은 플랫폼 출시 작업에서 따로 정한다.
- 이전 결정은 무료 플랜으로 시작하는 것이다. 클립과 주간 영상을 Storage에 올리면 무료 플랜의 용량·전송 한도를 넘길 수 있다. 미디어 단계(10절 5단계) 전에 예상 보관량을 계산하고 플랜 전환 기준을 정한다. 기준은 11절의 결정 항목이다.
- 로그인은 기존 결정인 이메일 OTP로 시작한다. 실제 발송 설정과 재전송 제한을 시험한다. 향후 플랫폼 로그인은 같은 사용자 계정에 연결하는 방식으로 확장한다. [이메일 OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless)

| 2. Supabase 기반 | Auth, 테이블, RPC, RLS, private channel, snapshot·cursor, 멱등 처리 | 두 사용자 격리와 늦은 커밋·재전송·복구 시험 통과 |
| 3. 데이터 실시간 연결 | 할 일·프로젝트·기록·티켓·템플릿·설정·완료 상태 | 두 기기 생성·수정·삭제·정렬 전파, 오프라인 병합 |
| 4. 공유 타이머 | 모든 타이머·체크인 명령, 정산, 작업 삭제와 전환, 부가 동작 제어 | 동시 조작과 종료에서도 기록·티켓·후속 작업 중복 없음 |
| 5. 이미지·영상 | asset 이전, Storage, 파일 큐, 배달 읽음 상태, 삭제 | 새 기기에서 표지·클립·주간 영상 복구 및 재생 |
| 6. 플랫폼 검증·출시 준비 | 브라우저 어댑터 시험, 프로토콜 버전, 재접속·절전·시간대·계정 전환 | Mac 두 인스턴스와 브라우저의 동일 결과. 공개 연동 기능은 필수 범위 검증 후 출시 |

단계 3 완료만으로 이번 요구 전체가 완료됐다고 보고하지 않는다. 실제 버전 번호와 출시일은 구현·검증 후 정한다. 기존 문서의 0.5.0 일정은 이번 계획의 배포 약속이 아니다. 로컬에 `release/0.5.0` 브랜치가 `feature/tomato-growth`와 같은 커밋으로 만들어져 있다. `release/*` 푸시는 정식 배포를 시작하므로 이번 계획의 구현과 검증이 끝나기 전에는 푸시하지 않는다.

핵심 검증 시나리오:

- A에서 시작 → B에 같은 남은 시간 → B에서 일시정지 → A도 정지 → A에서 재개.
- A와 B의 동시 시작·종료·체크인, 집중 중 할 일 삭제, 휴식 전환에서 서버 확정 결과가 하나로 수렴.
- 응답 유실 후 재전송, 구독 중단 중 변경, 절전 복귀, 기기 시계 차이, 서버 epoch 변경.
- 오프라인 양쪽 수정과 실행, 같은 필드 충돌, 삭제 후 오래된 기기 재접속, 파일 업로드 중 앱 종료.
- 두 계정의 데이터·큐·파일 격리, 연동 해제 중 변경 후 재활성화, 인증 만료 후 복구.
- 과거 기록과 티켓·클립 연결 보존, 다른 기기에서 촬영창·영상 생성 중복 방지.
- 일반 변경 지연과 타이머 표시 오차를 기록해 목표 충족 여부 확인.

구현 변경에 따라 `npm run check`, `npm test`, `npm run build`, 관련 Playwright와 Supabase DB 통합 시험을 수행한다. 구현 검증 결과와 실제 Supabase에서 추가 확인할 범위는 `supabase-sync-operations.md`에 기록한다.

## 11. 확정한 결정과 카피

2026-10-26 사용자가 수정 계획을 그대로 구현하도록 지시했다. 기기별 선택형 연동, 계정당 공유 타이머 하나, 이미지·영상 포함, 연동 해제와 서버 삭제 분리, 브라우저 시험 클라이언트, 추가·갱신 방식의 가져오기를 적용한다.

추가 질문에는 “기본값으로 진행”으로 답변했다.

- JSON 내보내기는 현재처럼 데이터만 포함한다.
- 일시정지 세션은 자동 종료하지 않는다.
- 겹친 오프라인 기록은 해결 대기로 보존하며 자동 합산하지 않는다.
- 유료 플랜 자동 전환 없이 용량 제한에 도달하면 파일 전송만 중단한다.

카피 수정 요청은 글자 그대로 반영한다.

1. 연동 안내: `연동하면 다른 기기와 동기화되어 사용하실 수 있습니다.`
2. 가져오기 안내: 제거. 대체 설명을 추가하지 않는다.
3. 계정 삭제 안내: `서버에 저장된 계정, 동기화 데이터와 파일을 삭제합니다. 이 기기에 저장된 데이터는 남습니다.`

기능에 필요한 최소 항목 이름과 버튼으로 `연동`, `연동 해제`, `지금 동기화`, `전송 대기`, `파일 전송 대기`, `연동 전 타이머`, `동기화 충돌`, `타이머 적용`, `별도 보관`, `보관된 기록`을 사용한다. 기존 로그인·로그아웃·이메일·인증 코드 문구는 유지한다. 오류는 연결 실패, 저장 용량, 계정 변경 등 처리 실패의 원인만 표시한다.

2026-10-26 첫 실행 안내와 로그인·회원가입 화면의 문구를 승인했다.

1. 안내 1단계 제목: `일단 3번만 해봅시다. 토오오오마토.` 사용자가 직접 수정했다. 랜딩 페이지 문구는 바꾸지 않았다.
2. 안내 1단계 설명과 2~4단계는 랜딩 페이지 문구를 그대로 쓴다.
3. 버튼: `다음`, `이전`, `건너뛰기`, `시작`, `로그인 없이 시작`, `나중에`. 탭과 버튼: `로그인`, `회원가입`.
4. 오류: `가입된 계정이 없습니다. 회원가입을 진행하세요.`

2026-10-27 사용자가 로그인과 회원가입을 하나로 합치도록 결정했다. 탭 없이 이메일과 인증 코드만 받고 버튼은 `로그인`이다. 처음 쓰는 이메일은 인증 때 계정이 만들어진다. `회원가입` 탭과 위 4번 오류 문구는 쓰지 않는다.

운영 서버 리전과 최종 서비스 용량, 다른 플랫폼의 출시 순서·버전은 정하지 않았다. 개인정보 처리방침·이용약관은 사용자 문구로 공개 배포 전에 준비한다.
