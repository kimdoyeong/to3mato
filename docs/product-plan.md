# To3mato 제품 기획서

작성일: 2026-10-19  
상태: 제품 방향 초안. 기본 화면 구조와 탭 구성을 정했으며 상세 화면과 동작은 후속 논의에서 결정한다.

To3mato는 무엇을 해야 할지 막막한 사람이 할 일을 찾고 하루를 정리하며 실행하도록 돕는 생산성 앱이다. 투두리스트와 포모도로와 캘린더를 결합하고 모든 계획과 실행의 기준을 포모도로로 통일한다.

> 딱 3번만 해봅시다. 토마토, 토마토, 토마토!

## 제품 비전

사용자가 자신의 하루를 구성하고 실행하는 과정을 연결하는 슈퍼 프로덕티비티 앱을 지향한다. 해야 할 일을 발견하는 순간부터 오늘 할 몫을 정하고 집중한 결과를 다음 계획에 반영하는 순간까지 돕는다.

제품의 복잡성은 사용자가 다루는 단위의 수로 늘어나지 않아야 한다. 투두리스트와 캘린더와 타이머를 오가더라도 같은 작업과 포모도로를 다룬다.

## 대상 사용자와 문제

초기 대상은 하루 동안 무엇을 해야 할지 정하기 어려운 사람이다. 이미 작업 목록이 있는 사람뿐 아니라 해야 할 일을 찾는 단계의 사람도 포함한다. 순서가 있는 학습은 활용 사례 중 하나이며 대상 사용자를 학습자로 한정하지 않는다.

| 사용자 상황 | 해결할 문제 |
| --- | --- |
| 하고 싶은 일과 해야 할 일이 막연하다. | 실행할 수 있는 할 일을 찾고 구체화하기 어렵다. |
| 여러 일이 머릿속에 흩어져 있다. | 오늘 무엇부터 얼마나 할지 정하기 어렵다. |
| 작업에 걸릴 시간을 예상해야 한다. | 처음 해보는 일을 몇 분으로 추정해야 할지 감이 오지 않는다. |
| 계획보다 늦게 시작했다. | 시작 시각이 어긋난 것만으로 하루 계획을 실패했다고 느낀다. |
| 일을 해봤지만 다음 계획에 반영하지 못한다. | 자신에게 맞는 작업량을 계속 새로 추측한다. |

## 포모도로로 통일하는 철학

포모도로는 계획량을 표현하는 단위이자 실제로 집중하는 단위다. 사용자는 세밀한 시간 견적 대신 대략적인 포모도로 수로 계획한다.

- 작업을 계획할 때: 이 일은 몇 포모도로 할까?
- 하루를 구성할 때: 오늘은 몇 포모도로 할 수 있을까?
- 캘린더에 배치할 때: 어느 날에 어떤 일을 몇 포모도로 할까?
- 실행할 때: 지금 이 포모도로를 시작하자.
- 돌아볼 때: 실제로 몇 포모도로가 필요했고 얼마나 더 필요할까?

포모도로의 길이와 휴식 방식 등 세부 설정은 별도로 결정한다. 이름과 캐치프레이즈의 숫자 3은 현재 단계에서 하루 사용량 제한이나 의무 횟수를 의미하지 않는다.

## 느슨해도 유지되는 하루 계획

10:30에 작업을 시작하려 했지만 스터디카페에 10:40에 도착할 수 있다. 이는 시작이 늦어진 상황이다. 하루 전체의 계획이 실패한 것은 아니다.

To3mato는 정확한 시작 시각보다 할 일의 순서와 포모도로 분량을 중심으로 계획을 구성한다. 도착해서 이 작업을 2포모도로 한다는 계획은 10:40에도 유효하다.

- 정확한 시작 시각 입력을 계획의 필수 조건으로 삼지 않는다.
- 시작이 늦어져도 예정된 첫 포모도로부터 실행할 수 있게 한다.
- 시각이 지났다는 이유만으로 작업을 실패나 지각으로 표시하지 않는다.
- 실제로 하루의 여유가 줄었다면 남은 포모도로 중 오늘 할 몫을 조정할 수 있게 한다.

느슨함은 사용 가능한 시간의 한계를 없애는 것이 아니다. 작은 지연 때문에 계획 전체를 다시 작성할 필요가 없도록 하는 것이다.

## 실행 경험으로 계획 보정하기

처음에는 대략 계획하고 실제로 해본 기록을 바탕으로 다음 계획을 더 정확하게 잡는다. 분 단위를 포모도로 수로 바꾸는 데서 끝나지 않고 경험이 다음 예상으로 이어져야 한다.

| 구분 | 의미 |
| --- | --- |
| 처음 예상 | 작업을 시작하기 전에 필요하다고 생각한 포모도로 수 |
| 실제 사용 | 작업에 실제로 사용한 집중량 |
| 남은 예상 | 현재 시점에서 작업을 마치기 위해 더 필요하다고 생각하는 포모도로 수 |

처음 예상과 실제 기록을 보존해야 자신의 추정 습관을 이해할 수 있다. 작업을 조정하더라도 이전 실행 기록은 유지한다.

집중량과 작업 완료 여부는 구분한다. 예상한 포모도로를 전부 사용했다는 사실만으로 작업을 자동 완료하거나 진척률을 단정하지 않는다. 실제 진척을 확인한 뒤 남은 분량을 조정한다.

이전 기록을 보여주는 방식과 비슷한 작업을 판단하는 기준 및 자동 추천 여부는 후속 설계에서 결정한다.

## 투두리스트와 캘린더와 타이머의 결합

| 구성 | 제품 안에서의 역할 |
| --- | --- |
| 투두리스트 | 실행할 일을 담고 필요한 포모도로 분량을 정한다. |
| 캘린더 | 날짜별로 할 일과 포모도로 분량을 배치하고 여러 날의 계획을 살펴본다. |
| 포모도로 타이머 | 계획한 작업을 실행하고 실제 집중 기록을 남긴다. |

작업 하나가 여러 날에 걸쳐 이어질 수 있다. 작업 전체에 필요한 분량과 오늘 할 몫을 구분한다. 예를 들어 제안서 작성에 4포모도로를 예상하고 오늘 2개와 내일 2개를 배치할 수 있다.

계획한 작업에서 바로 집중을 시작할 수 있어야 한다. 실행 후에는 같은 작업의 진척과 기록을 확인하고 남은 계획을 조정한다.

## 하루가 정리되는 경험

사용자는 하루 계획을 구성한 뒤 다음을 알 수 있어야 한다.

1. 오늘 무엇을 할 것인가.
2. 어떤 순서로 할 것인가.
3. 오늘은 어디까지 할 것인가.

할 일을 발견하고 구체화하도록 돕되 모든 생각을 오늘의 의무로 만들지 않는다. 오늘 사용할 수 있는 포모도로 안에서 할 몫을 정한다. 아직 오늘 하기로 정하지 않은 일도 보관하고 나중에 계획할 수 있어야 한다.

할 일 발견을 돕는 구체적인 방식은 아직 정하지 않았다. 질문형 안내와 직접 입력 및 다른 방식의 적합성을 화면 설계에서 검토한다. AI 사용 여부도 확정하지 않는다.

## 기본 화면 구성

화면은 왼쪽 작업 영역과 오른쪽 실행 영역으로 나눈다.

왼쪽 작업 영역의 좌측에 세로 내비게이션을 두고 다음 순서로 구성한다.

1. 할 일 (Todo)
2. 프로젝트
3. 캘린더
4. 설정

오른쪽에는 별도의 내비게이션을 두지 않는다. 왼쪽 탭을 전환하는 동안에도 실행 영역은 유지된다.

오른쪽 실행 영역은 다음으로 구성한다.

1. 타이머
2. 액션 버튼
3. 오늘 할 일 목록

오늘 할 일의 각 항목에는 재생(play) 버튼을 둔다. 사용자가 재생 버튼을 누르면 해당 할 일을 대상으로 타이머가 실행되고 시간 기록이 시작된다. 실행 기록은 선택한 할 일에 연결한다.

### 작업 전환과 포모도로 기록

A 작업 실행 중 B 작업의 재생 버튼을 누르면 A의 시간 기록을 멈추고 B로 전환하여 시간 기록을 시작한다.

전환으로 중단된 집중량은 0포모도로와 0.5포모도로 및 1포모도로 중 가장 가까운 값으로 반올림해 기록한다. 이전에 완료한 포모도로 기록은 유지한다. 실제 집중 시간과 반올림한 포모도로 수는 구분한다.

B로 전환하면 설정된 포모도로 전체 시간으로 새 타이머를 즉시 시작한다. A에서 남은 시간이나 B의 이전 중단 시간을 이어받지 않는다.

각 탭의 상세 내용과 프로젝트의 구성 방식은 후속 설계에서 결정한다. 이전 실행 기록을 확인하는 위치도 이 구조 안에서 정한다.

## 핵심 사용자 흐름

할 일 발견 → 실행할 작업으로 구체화 → 포모도로 분량 예상 → 날짜와 순서 배치 → 집중 실행 → 진척 확인 → 다음 계획에 반영

예시:

1. 사용자가 제안서를 준비해야 한다는 생각을 작업으로 정리한다.
2. 작업에 4포모도로가 필요할 것으로 대략 예상한다.
3. 오늘 2포모도로와 내일 2포모도로를 배치한다.
4. 예상보다 늦게 도착해도 오늘의 첫 포모도로부터 시작한다.
5. 오늘 2포모도로를 실행한 뒤 실제 진척을 확인한다.
6. 남은 분량이 3포모도로라면 내일 할 몫을 다시 정한다.
7. 다음에 비슷한 작업을 계획할 때 이번 기록을 참고한다.

## 제품 문체와 이름

제품명은 To3mato다. o 세 개를 o3로 표현한다는 이름 아이디어에서 출발했으며 토마토와 포모도로의 연결을 유지한다.

대표 문구는 다음을 사용한다.

> 딱 3번만 해봅시다. 토마토, 토마토, 토마토!

앱의 UI 문구는 기능과 상태 및 처리 결과를 직접 설명한다. 버튼과 입력 항목은 짧은 명사형으로 쓴다. 안내와 오류는 필요한 정보를 간결한 문장으로 전달한다. 감성적인 격려와 수사적 질문 및 장식성 설명은 사용하지 않는다.

## 기술 스택

To3mato는 Electron + Vite + Svelte로 구현한다.

| 기술 | 역할 |
| --- | --- |
| Electron | 데스크톱 앱 실행과 운영체제 기능 연동 |
| Vite | 개발 서버와 빌드 |
| Svelte | 화면 구성과 UI 상태 처리 |

화면 구현은 다른 에이전트가 완료한 최신 디자인을 기준으로 한다. 개발과 확인은 로컬에서 진행한다.

## 초기 설계 범위 제안

첫 설계에서는 아래 흐름을 연결한다. 개별 기능의 상세 범위와 개발 순서는 화면 구성을 논의한 뒤 결정한다.

- 남은 분량과 다음 계획 조정하기
